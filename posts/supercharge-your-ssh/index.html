Supercharged ⚡️ SSH

I have been working with servers for quite a few years now and SSH has become a swiss army knife of functionality for far more than just remote logins.

It all started out with storing the credentials in a simple spreadsheet/CSV file and copy-pasting the details in the terminal. Over the years, the servers have grown from a handful to ~50 plus and counting. And this has made the spreadsheet/CSV archaic to work with.

What follows is a list for some of my use cases that leverage the power of ssh. These usecases might be simplified or be baked-in in certain ssh/linux flavours. However, I had to hit the internet and script them for my work and personal laptops.

SSH Config and Aliases

This was my initial approach at sharpening my axe. Put all the details in a config file and use friendly aliases to use those details and connect to the server. A few quick searches on the internet led me to ~/.ssh/config file where I could store my SSH configuration and custom aliases.

# ~/.ssh/config

### default for all ##
Host *
    ForwardAgent no
    ForwardX11 no
    ForwardX11Trusted yes
    IdentitiesOnly yes
    Protocol 2
    ServerAliveInterval 60
    ServerAliveCountMax 30
    StrictHostKeyChecking no
    IdentityFile "~/.ssh/id_rsa.pem"
    IdentitiesOnly yes

## override as per host ##
Host myproject
    HostName 1.2.3.4
    User appuser
    Port 1234
    IdentityFile "~/.ssh/keyfile2.pem"

Host myproject2
    HostName 10.20.30.40
    User appuser
    PubkeyAuthentication no
    # Password - sup3rs3cr3tpassw0rd

This configuration did not support password based SSH logins. There was no way to make SSH use an external tools (e.g. password managers, osx keychain, etc.) to import passwords from when connecting to remote servers having passwords. The web suggested at using sshpass cli-tool for password support and shift the SSH configuration to shell scripts. An approach I was not too keen about.

So I resolved to manually type the passwords and use the inbuilt functionality of the SSH config file. Now I could simply use ssh myproject instead of ssh -i ~/.ssh/keyfile2.pem appuser@1.2.3.4 -p 1234. For passwords, I created a small helper alias - alias cssh="cat ~/.ssh/config" - in my ~/.bashrc. This would help me quickly lookup the password and then use the alias to connect to the server.

Managing Multiple SSH Config Files

Now while the above approach worked flawlessly, my ssh-config file soon became grew to about 500+ lines of configuration for different servers and users on those servers. Admin users and regular users connections to the same sever were a different configuration entries. Managing all this in a single file was a task.

Thinking about how to overcome this, I came up with an idea of splitting the configuration file in to multiple files, and then sourcing them into a master config file. Similar to how one would include a SCSS partial into a main file or an import statement in NodeJS.

A few internet searches later I found out that OpenSSH did support an include directive to source multiple configuration files into a master config file. Now this directive has been there since 2005, however the SSH program that came with my OSX system didn’t support it and I was not keen on implementing Tim Hilliard’s solution to replace it.

So I went about managing this in a folder/file structure format and figuring out a way to merge all the files in one. I was confidant that I could put together a quick and dirty script to merge all the configuration files.

~/.ssh/
├── id_rsa.pem
├── id_rsa.pub
├── include_conf
│   ├── ssh_base_config   <- default values for all ssh connections
│   ├── sshconfig_group1  <- configuration for a group of servers
│   ├── sshconfig_group2
│   └── sshconfig_group3
├── config                <- merged master ssh config file
├── keys                  <- keys for different servers
│   ├── key1.pem
│   ├── key2.pem
│   └── key3.pem
└── known_hosts

With this approach I could use a naming convention and have a logical separation of SSH connections. I chose to go ahead by grouping them on a project basis with all servers related to a project present in one file.

# sshconfig_group1

Host myproject_app
    HostName 1.2.3.4
    User appuser
    Port 1234
    IdentityFile ~/.ssh/key1.pem

Host myproject_app_root
    HostName 1.2.3.4
    User root
    Port 1234
    IdentityFile ~/.ssh/key2.pem

Host myproject_db
    HostName 2.2.3.4
    User dbuser
    Port 1234
    IdentityFile ~/.ssh/key1.pem

Host myproject_db_root
    HostName 2.2.3.4
    User root
    Port 1234
    IdentityFile ~/.ssh/key2.pem

I wrote a simple compile-ssh() shell function in my ~/.bashrc to merge all the configuration files into a single file. Good old internet did give me some inspiration for this function. Looks like this is a common problem that a lot of folks have been facing.

# Compile multiple ssh configs into master file
function compile-ssh() {
    curr_date="$(date '+%Y%b%d-%H%M%S')"
    touch $HOME/.ssh/config
    echo "# Compiled On: $(date '+%d-%b-%Y %H:%M:%S %Z')" > $HOME/.ssh/config
    [[ -f $HOME/.ssh/include_conf/ssh_base_config ]] && cat $HOME/.ssh/include_conf/ssh_base_config >> $HOME/.ssh/config
    cat $HOME/.ssh/include_conf/sshconfig_* >> $HOME/.ssh/config
}

With this, I had sanity in managing servers and knew that this was a scalable approach that I could stick to in the long run.

SSH Tab Completion - Why not?

I still had to type out the full server alias before I could connect to the server. A trade-off that I had not given too much thought to. Pretty soon with my naming convention - <project>_<server type>_<is root> - I had long aliases and an I wished for some sort of tab completion. For the life of me, I didn’t bother looking into this. I was under the assumption that since this is a file I generated with a shell function, there wouldn’t be much information on reading from a file and adding data to autocompletion.

Little did I know, that it was quite the opposite. I had forgotten that the file I was generating had a standard format which the SSH program can parse. The internet did have a solution to this and some how without conciously searching for it I stumbled accross it.

# ~/.ssh-completion

_ssh()
{
    local cur prev opts
    COMPREPLY=()
    cur="${COMP_WORDS[COMP_CWORD]}"
    prev="${COMP_WORDS[COMP_CWORD-1]}"
    opts=$(grep '^Host' ~/.ssh/config ~/.ssh/config.d/* 2>/dev/null | grep -v '[?*]' | cut -d ' ' -f 2-)

    COMPREPLY=( $(compgen -W "$opts" -- ${cur}) )
    return 0
}
complete -F _ssh ssh

Adding [[ -f $HOME/.ssh-completion ]] && source $HOME/.ssh-completion to ~/.bashrc was the only thing left to start tabbing all my SSH connections.
