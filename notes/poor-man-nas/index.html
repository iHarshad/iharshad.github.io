Goal

Auto-mount USB storage when plugged in, expose as a Samba share. Share disappears when drive is unplugged. Existing [jellyfin] share is unrelated and working.

Files on server

FileDescription
/etc/udev/rules.d/99-usb-hdd.rulesudev rule that triggers mount/umount scripts when a USB block device is added or removed
/usr/local/bin/mount-usb.shMounts the USB partition, reads label+size, calls the Samba add script, reloads smbd
/usr/local/bin/umount-usb.shCalls the Samba remove script, reloads smbd, then unmounts and removes the mount point
/usr/local/bin/samba-usb-add.pyAdds a [usb-{label}-{size}] share entry to /etc/samba/smb.conf
/usr/local/bin/samba-usb-remove.pyRemoves the share entry from /etc/samba/smb.conf by matching the mount path

How detection works

The kernel detects USB storage the moment a drive is physically connected (or present at boot). It registers it as a block device (e.g. /dev/sda, /dev/sda1).

udev watches for these kernel events and fires rules from /etc/udev/rules.d/99-usb-hdd.rules:

  • Plug in / boot with drive connected — kernel emits an add event for the partition (e.g. sda1). udev matches it against the rule (SUBSYSTEM=="block", KERNEL=="sd[a-z][0-9]", SUBSYSTEMS=="usb", filesystem type present) and runs mount-usb.sh via systemd-run. The script mounts the partition to /mnt/usb-<UUID>, adds the Samba share, and reloads smbd. The share appears on the network within a few seconds.

  • Unplug / safe remove — kernel emits a remove event for the partition. udev matches it and runs umount-usb.sh via systemd-run. The script removes the Samba share entry, reloads smbd, unmounts the partition, and deletes the mount point directory. The share disappears from the network immediately.

There is no polling — everything is event-driven. No manual intervention needed.

What was broken

Bug 1 (critical): Wrong udev bus condition The rule used ENV{ID_BUS}=="usb" but USB storage devices expose through the kernel SCSI layer, so ID_BUS is always scsi. The rule never matched, so the scripts never ran. Fix: use SUBSYSTEMS=="usb" (plural — walks up the device parent tree to find the USB ancestor).

Bug 2: systemctl fails silently from udev udev’s RUN+= context has no D-Bus socket, so systemctl restart smbd silently failed even if the mount succeeded. Fix: wrap with /usr/bin/systemd-run --no-block so the script runs as a transient systemd unit with full environment.

Also switched restart → reload (sends SIGHUP, picks up new shares without dropping existing connections).

Share naming

Share name format: usb-{label}-{size} e.g. usb-Seagate-Backup-Plus-Drive-2TB

  • Label comes from the disk’s filesystem label (blkid -s LABEL)
  • Size computed from /sys/class/block/<dev>/size (sectors × 512)
  • Falls back to usb-{uuid[:8]}-{size} if no label is set
  • Remove script finds the share by path match (not name), so it works regardless of name format

Scalability & behaviour with multiple drives

The setup handles multiple drives without any changes. Each drive goes through the same udev → script pipeline independently.

What works well:

  • Each partition gets its own mount point (/mnt/usb-<UUID>) and its own Samba share, so drives don’t interfere with each other.
  • Drives can be connected or removed in any order and at any time — each event is handled independently.
  • A drive with multiple partitions (e.g. sda1, sda2) gets a separate share per partition.
  • UUIDs are used as mount point names, so the same drive always mounts to the same path regardless of which USB port it’s plugged into or what device name the kernel assigns (sda, sdb, etc.).

Pain points:

  • Name collisions — if two drives have the same filesystem label (e.g. both labelled “My Drive”), they’ll generate the same share name and the second one will silently not be added to smb.conf. Workaround: relabel one of the drives.
  • No partition filtering — if a drive has a small utility/recovery partition alongside the main data partition, both get shared. Can be annoying with drives that have hidden EFI or vendor partitions.
  • Unclean NTFS drives — if a Windows drive wasn’t safely ejected, ntfs-3g tries to fix it on mount. This adds a few seconds delay and occasionally fails, leaving the drive unmounted with no visible error.
  • smb.conf written as ini — Python’s configparser rewrites the entire smb.conf on every add/remove. Comments and formatting in the original file are lost after the first write. The [jellyfin] share content is preserved but its comments are stripped.
  • No retry on failure — if the mount fails (e.g. unclean NTFS that can’t be auto-fixed), nothing retries. The drive just stays unmounted silently. Check journalctl -u 'run-*.service' to see errors from the transient systemd units.
